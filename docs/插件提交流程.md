# 插件提交流程

Picora 的[模块仓库](https://github.com/Alnitak44/picora-plugins)收录插件登记信息。插件源码和 ZIP 由作者在自己的公开 GitHub 仓库维护；首次收录提交一份登记文件，后续版本由模块仓库从 GitHub Release 自动获取。

## 首次投稿

1. 按 [插件协议](PLUGINS.md)制作插件，在 Picora 中用本地 ZIP 测试。新插件 ID 使用 `io.github.<GitHub 用户名小写>.<插件名>`，并保持稳定。ZIP 根目录需有 `plugin.json`、入口 JSON、`readme.md` 及所引用的资源。
2. 在自己的公开 GitHub 仓库发布 Release，将 `.picora-plugin.zip` 文件上传为 Release 附件。Release 标题可自定；建议标签与插件版本对应，例如 `v1.0.0`。不要只依赖 GitHub 自动生成的 Source code ZIP。
3. Fork [模块仓库](https://github.com/Alnitak44/picora-plugins)，参考 [ImgBB 登记示例](https://github.com/Alnitak44/picora-plugins/blob/main/examples/io.github.ruzmarin.picora.imgbb.json)，新增 `registrations/<插件 ID>.json`，然后向模块仓库的 `main` 分支提交 PR。登记文件需填写：
   - `id`：与 ZIP 内 `plugin.json` 的 ID 完全一致。
   - `releaseRepository`：作者的 `用户名/仓库名`；`plugin.json` 的 `repository` 应指向同一仓库。
   - `minAppVersion`：插件要求的最低 Picora 版本；`http-v2` 至少为 `1.0.1`。
   - `approvedPermissions`：与入口 JSON 的 `permissions` 对应，尤其要准确列出网络目标。
4. PR 的 CI 从 Release 读取 ZIP，验证包结构、ID、版本、运行时和权限。维护者审核后合并；模块仓库自动生成客户端读取的 `index.json` 和插件列表。

投稿时无需填写下载地址、ZIP 大小或 SHA-256，也无需将 ZIP 或源码复制到模块仓库。

## 发布更新

保持插件 ID 不变，在作者仓库发布版本号递增的新 Release，并上传新的 `.picora-plugin.zip` 附件。模块仓库定时检查 Release；验证通过后自动更新目录。不要用不同内容覆盖已发布版本的附件。

如果新版本改变了网络目标、不安全 HTTP 或云端删除权限，应先修改模块仓库中的登记文件并提交 PR，说明变化，等待审核；审核通过后再发布新 ZIP。Picora 用户安装更新时仍会看到插件的实际权限。

## 目录如何工作

客户端从模块仓库的 `main/index.json` 读取目录，下载 GitHub Release 中的插件 ZIP。目录缓存 12 小时，可手动刷新；连接失败时使用上次有效目录。GitHub 镜像仅在客户端下载目录和 ZIP 时应用，不用于图床上传或插件认证。

`index.json` 由模块仓库生成，包含插件元信息、下载地址、ZIP 字节数与 SHA-256，供客户端核对身份和完整性。投稿者只编辑登记文件，不直接修改 `index.json`。插件源码与许可证归作者维护；目录合并由维护者审核请求目标、凭证使用及删除语义。
